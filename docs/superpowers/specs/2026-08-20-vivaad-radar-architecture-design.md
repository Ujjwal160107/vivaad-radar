| 4. Matching engine | Designed here (pipeline s3–s5); blocked on step 2 |
| 5–13 | Designed here; not started |

Decisions already made from the data (by teammate, confirmed):

- **District: Sultanpur (UP)** — 81 parcels, 63 cases, 23 villages, 14 sub-divided IDs, 11 dispute types. Resolves §68's blocking question.
- **Flagship RED case (Parcel B, §50):** CNR `UPHC020611812025` (WRIB/784/2025), *Shyamdhar Dubey and 9 others v. Deputy Director of Consolidation, Sultanpur*. Parcels Gata 153 and 1365/1 (sub-divided — the PRD's "45/1" story), village Madanpur Paniyar, 1 bigha, relation "Santu s/o Bhola", filed 2025-08-11, **active** (`is_final = False`), satisfying §30's RED requirement.
- 12 active parcel-bearing cases available for RED; 30 disposed ones for the GREEN-with-history path.

**Hard requirements on the parcel file:**

1. **Parcel B must exist**: `survey_no` matching Gata 153 / 1365/1, village Madanpur Paniyar, owner name fuzzily related to "Shyamdhar Dubey". Without it the flagship RED cannot fire.
2. **Parcel A must exist**: a clean parcel with zero candidate case links (GREEN).
3. At least one `land_events` sale date must fall **inside** the flagship litigation window (filed → next hearing) — the timeline's emotional beat (§51 step 4) depends on it.
4. Include §22's full decoy set: true links, AMBER ambiguities, name-collision false positives, survey-number format variants, transliteration variants.

## 5. Pipeline (staged offline build)

Each stage reads the previous stage's output, writes its own inspectable artifact to `data/intermediate/`, and is independently re-runnable. `run_all.py` executes s1→s7.

| Stage | Responsibility | Output |
|---|---|---|
| **s1_ingest** | Read both parquets; validate contract (required columns present, flagship case AND flagship parcel present — fail loudly at build time, never at demo time); tag every row with a §21 provenance label (real / synthetic / derived) | `cases.json`, `parcels.json` |
| **s2_normalize** | Survey-number normalization (`142/3` ≡ `142-3` ≡ `142 / 3`); name normalization (lowercase, strip honorifics, standardize `S/o`/`D/o`); build village gazetteer from the parcel file | `normalized.json` |
| **s3_candidates** | Blocking: pair case × parcel only when village matches; case with null village → district-wide candidates, flagged `location_unconfirmed` | `candidates.json` |
| **s4_score** | §27 features per pair: exact survey match, normalized survey match, village/taluk match, RapidFuzz token-sort name similarity, father-name similarity, case-type relevance. Weighted sum (0.4 / 0.25 / 0.15 / 0.1 / 0.1). Band per §28 (HIGH ≥ 0.85 + identifier match; MEDIUM 0.6–0.85; LOW < 0.6). Store per-pair evidence JSON — this is the methodology panel's data source | `links.json` |
| **s5_status** | §30 status engine, pure rules: worst-case wins per parcel; RED requires HIGH band + identifier match + active case; unknown case status caps at AMBER; closed HIGH-confidence link → GREEN with "closed litigation history" note; incomplete data degrades to AMBER, never silently GREEN | `parcel_status.json` |
| **s6_load_db** | Write all eight §19 tables (Parcel, Person, CourtCase, CaseParty, CourtEvent, ParcelCaseLink, Watchlist, SourceRecord) into `vivaad.db` | `vivaad.db` |
| **s7_export_fallback** | Render every §37 endpoint response for every parcel to `data/output/fallback/` (tier 2), plus hardcoded flagship payloads (tier 3) | `fallback/*.json` |

**ML boundary (§40):** RapidFuzz fuzzy similarity inside s4 is the shipping baseline. Any future NER/embedding enhancement is a drop-in replacement for a single feature function in s4 — no other stage changes. ML is never load-bearing for the demo (§42).

## 6. Backend (FastAPI, read-only)

```
backend/
├── main.py            # app + router registration
├── db.py              # SQLite connection (reads everywhere; writes only via watchlist router)
├── routers/
│   ├── parcels.py     # GET /parcels/search, /parcels/{id}, /parcels/{id}/litigation
│   ├── cases.py       # GET /cases/{id}
│   ├── dashboard.py   # GET /dashboard/overview, /dashboard/heatmap
│   └── watchlist.py   # POST/GET /watchlist
└── fallback.py        # middleware: DB missing/query failure → serve fallback JSON
```

Rules:

- Exactly the eight §37 endpoints. No more.
- **No scoring, matching, or ML at query time** (§36, §48) — every endpoint is a SELECT plus JSON shaping. Target latency: low hundreds of milliseconds.
- `GET /parcels/{id}/litigation` returns the exact response shape written in §37 so the linkage output drops in unmodified.
- Watchlist is the single write path: one INSERT; the "new update" badge is a scripted flag column, not a real notification (§34).
- Failed lookup → structured "not found — check spelling/format" payload (§16). Internal failure → fallback middleware serves cached JSON silently. A judge never sees a stack trace.

## 7. Frontend (React + Vite + Tailwind + Leaflet)

```
frontend/src/
├── pages/
│   ├── Search.tsx           # screen 1 — "Is this land in court?"
│   ├── Processing.tsx       # screen 2 — the 5 named pipeline steps (§16)
│   ├── Result.tsx           # screens 3/4/5 — one component, status-driven
│   ├── CaseDetail.tsx       # screen 6
│   ├── OfficerDashboard.tsx # screens 8/9 — heatmap + drill-down
│   └── Watchlist.tsx        # screen 10
├── components/
│   ├── Timeline.tsx         # screen 7 — the "aha" (§14); highest-craft component
│   ├── EvidencePanel.tsx    # screen 11 — matched fields + confidence explanation
│   ├── StatusBadge.tsx      # G/A/R badge with §46 copy baked into the component
│   └── ParcelMap.tsx        # Leaflet, GeoJSON polygons coloured by status
└── api/client.ts            # typed fetch wrapper over the 8 endpoints + tier-3 payloads
```

Design constraints enforced structurally, not by discipline:

- `StatusBadge` renders the mandatory §46 copy ("GREEN ≠ legally safe", "evidence suggests", "consult a lawyer") as part of the component — no screen can omit it.
- `Processing.tsx` is a timed animation over the five named steps (finding parcel → extracting refs → resolving entities → checking cases → scoring). It reads no live state; it exists to make the linkage legible (§16).
- `Timeline.tsx` is plain SVG/divs on one horizontal axis — filed → interim order → **sale registered (visually highlighted as inside the pendency window)** → next hearing. No charting library.
- Mobile: search and result screens usable at phone width; officer map is desktop-first (§16).

## 8. Demo reliability tiers (§73)

| Tier | Mechanism | Trigger |
|---|---|---|
| 1 — Live | frontend → FastAPI → SQLite | Normal |
| 2 — Cached | `fallback.py` middleware serves s7-exported JSON; same URLs, frontend unaware | DB missing or query failure |
| 3 — Emergency | Flagship payloads (Parcel A GREEN, Parcel B RED) bundled as static imports in `api/client.ts` | `?demo=1` flag or failed fetch |

No tier touches the internet at demo time. Map tiles: schematic base or pre-downloaded tiles — no live tile server dependency.

## 9. Testing & evaluation

- **Golden-case test (automates §62's acceptance criterion):** after `run_all.py`, assert Parcel B is RED with confidence ≥ 0.85 and Parcel A is GREEN. Run on every data drop.
- **Matching metrics (§43/§44):** hand-label ~30 candidate pairs from `candidates.json` (true links, §22 decoys, hard negatives); report precision/recall honestly on the slide; report high-confidence precision specifically.
- **API smoke test:** hit all 8 endpoints against the built DB.
- **Frontend:** manual walkthrough of the §51 demo script; verify Result renders for all three statuses.
- Tooling: pytest + one shell script. Nothing more.

## 11. Timebox and cut order (§63)

Steps 1–7 of §62 (schema → data → extraction → matching → backend → citizen UI → timeline) are non-negotiable. Cut in reverse order under pressure: polish → evaluation → ML enhancement → watchlist → officer dashboard/map. The regex + RapidFuzz baseline is always the shippable path.

## 12. Guardrails (§72)

If anyone starts building auth, a chatbot, blockchain, OCR, generic complaint systems, full land-record CRUD, payments, or cloud infra — stop them. Nothing in this architecture requires or permits any of these.

## 13. Out of scope for this design

- Real notifications (watchlist is mocked, §34)
- Any live scraping or internet dependency at demo time
- Graph database (§38 — relational + link table is deliberate)
- Multi-district/multi-state support (roadmap §59, architecture is district-agnostic by construction)
